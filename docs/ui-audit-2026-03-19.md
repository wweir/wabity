# UI Audit Report

Date: 2026-03-19
Scope: launcher + settings UI in `src/app`, `src/features/launcher`, `src/features/settings`
Method: source inspection + local Playwright screenshots/DOM metrics

## Audit Premise

This repo does not provide explicit design context in `.impeccable.md`, and the current instructions do not define target emotional tone or brand system. Anti-pattern judgments below are therefore based on the product description in `README.md` and the current shipped interface, not on unstated brand intent.

## Anti-Patterns Verdict

Verdict: Fail

Does it look AI-generated? Yes, immediately.

Specific tells:

- `src/app/global.css` uses `Inter` / system fallback at the root, which is the safest possible default rather than a deliberate typographic choice.
- Both launcher and settings lean on the same pale frosted-glass treatment, rounded pills, thin beige borders, and low-contrast neutrals. That is generic “tasteful AI utility app” styling, not a distinct product language.
- Settings navigation is an identical pill grid with almost no hierarchy variance; it reads like a template, not an interface shaped around task frequency.
- Visual rhythm is flat. Most controls share the same radius, same border weight, same tonal range, and same spacing cadence.
- The launcher hero state is mostly empty pale space plus placeholder text. It feels unfinished rather than intentionally minimal.

This is not “bad because minimal”. It is bad because it is non-committal.

## Executive Summary

- Total issues: 11
- Critical: 1
- High: 3
- Medium: 4
- Low: 3
- Overall quality score: 58/100

Most critical issues:

1. The launcher’s primary input has no accessible name and relies on placeholder text.
2. The settings page exposes theme and font-size controls that are persisted but never applied.
3. The settings frame hard-locks to `920x720`, causing horizontal overflow on narrow viewports despite responsive CSS rules.
4. Popup semantics are inconsistent: menu/dialog claims do not match implemented roles or keyboard behavior.

Recommended next steps:

1. Fix launcher input labeling and popup semantics first.
2. Remove or implement fake appearance settings.
3. Repair settings frame sizing so CSS breakpoints can actually take effect.
4. Normalize tokens, contrast, and component sizing before any visual polish pass.

## Detailed Findings By Severity

### Critical Issues

#### 1. Launcher primary input has no accessible name

- Location: `src/features/launcher/components/LauncherComposer.tsx:169-206`
- Severity: Critical
- Category: Accessibility
- Description: The core launcher input renders without `label`, `aria-label`, or `aria-labelledby`. The only instruction is placeholder text. Playwright DOM sampling confirmed the input has `ariaLabel = null`, `ariaLabelledby = null`, `title = null`.
- Impact: Screen reader users cannot reliably identify the main control of the product. Because this is the primary action surface, it is a core-flow blocker, not a cosmetic defect.
- WCAG/Standard: WCAG 2.1 A `4.1.2 Name, Role, Value`; also collides with `3.3.2 Labels or Instructions`.
- Recommendation: Give the input a persistent programmatic label, then keep the placeholder only as an example/hint. If autocomplete is attached, wire the combobox relationship explicitly.
- Suggested command: `/harden`

### High-Severity Issues

#### 2. Theme and font-size settings are fake controls

- Location: `src/features/settings/SettingsPage.tsx:2702-2739`, `src/app/global.css:56`
- Severity: High
- Category: Theming
- Description: The settings UI exposes `theme` and `fontSize` selectors, but repo-wide search shows those values are only persisted, never consumed by runtime styling. `src/app/global.css` hard-forces `color-scheme: light`, and there is no `data-theme`, class toggle, or font-scale application path.
- Impact: Users are told they can change appearance, but nothing happens. That is a direct trust break and makes the settings page look unfinished or deceptive.
- WCAG/Standard: UX integrity issue; theming also conflicts with user expectation for system appearance support.
- Recommendation: Either implement runtime application of theme/font scale or remove the controls until real behavior exists.
- Suggested command: `/normalize`

#### 3. Settings frame sizing defeats responsive CSS and causes horizontal overflow

- Location: `src/features/settings/useSettingsWindowFrame.ts:5-47`, `src/features/settings/SettingsPage.tsx:2537-2542`
- Severity: High
- Category: Responsive
- Description: The frame is clamped to a minimum width of `520`, preferred width `920`, then forced inline via `width/maxWidth/height/maxHeight`. In browser inspection at a `600px` viewport, the settings frame remained `920px` wide and the page reported `scrollWidth 924 > clientWidth 600`.
- Impact: Breakpoints in `settings.css` cannot save the layout if the container itself never shrinks. On smaller screens or constrained windows, users get clipped content and horizontal reflow failure.
- WCAG/Standard: WCAG 2.1 AA `1.4.10 Reflow`
- Recommendation: Let CSS own width below breakpoints, or derive frame size from actual viewport width in browser mode instead of always forcing the Tauri-preferred frame.
- Suggested command: `/adapt`

#### 4. Popup semantics claim menu/dialog behavior that the implementation does not provide

- Location: `src/features/launcher/components/LauncherHeader.tsx:61-69`, `src/features/launcher/components/LauncherHeader.tsx:126-130`, `src/features/launcher/components/WorkspacePickerPanel.tsx:33-45`, `src/features/launcher/components/AgentPickerPanel.tsx:30-43`, `src/features/launcher/components/SessionPanel.tsx:44-48`
- Severity: High
- Category: Accessibility
- Description: Workspace and agent triggers announce `aria-haspopup="menu"`, but popup children are plain buttons without `menuitem` roles or menu keyboard behavior. The session trigger announces `aria-haspopup="dialog"` / `aria-controls`, but the target is a plain `<section>` with no dialog role or modal semantics.
- Impact: Assistive tech receives a misleading interaction model. Keyboard users and screen reader users get an interface that claims one behavior and performs another.
- WCAG/Standard: WCAG 2.1 A `4.1.2 Name, Role, Value`; WCAG 2.1 A `1.3.1 Info and Relationships`
- Recommendation: Pick one model and implement it correctly. For simple popovers, remove false ARIA. For actual menus/dialogs, add proper roles, focus management, and keyboard handling.
- Suggested command: `/harden`

### Medium-Severity Issues

#### 5. Launcher auto-resize path is mutation-heavy and likely to jank under stream updates

- Location: `src/lib/tauri/useAutoResizeWindow.ts:4-26`, `src/lib/tauri/useAutoResizeWindow.ts:55-66`, `src/features/launcher/LauncherPage.tsx:891`
- Severity: Medium
- Category: Performance
- Description: Every resize/mutation sync walks `querySelectorAll("*")` and calls `getBoundingClientRect()` on every visible descendant before issuing a resize command. The hook also subscribes to subtree mutations, character data, and attribute changes.
- Impact: Session streaming, expanding panels, or dense result updates can force repeated full-tree layout reads and window resize work. That is a classic jank source in a launcher where responsiveness is the product.
- WCAG/Standard: Performance issue, not a direct WCAG failure.
- Recommendation: Measure a smaller boundary, debounce harder, and stop scanning the full subtree for every update.
- Suggested command: `/optimize`

#### 6. Several interactive targets are too small for comfortable use

- Location: `src/features/launcher/launcher.css:62-70`, `src/features/launcher/launcher.css:247-253`, `src/features/launcher/launcher.css:319-323`, `src/features/launcher/launcher.css:798-806`, `src/features/settings/settings.css:264-287`
- Severity: Medium
- Category: Responsive
- Description: Measured launcher buttons include `27px`, `31px`, `32px` heights, the create-session button is `26x26`, and session dots are only `11x11`. The settings toggle is `44x24`, which is still a short vertical target.
- Impact: These controls are precision-heavy even for mouse users and clearly poor for touch, stylus, accessibility zoom, or motor impairments.
- WCAG/Standard: WCAG 2.2 AA `2.5.8 Target Size (Minimum)` is violated by the `11x11` dots; broader `44x44` ergonomics heuristic is also missed throughout.
- Recommendation: Raise the minimum interactive box size, especially on status dots, launcher chrome, and pill controls.
- Suggested command: `/adapt`

#### 7. Thought disclosure is click-only and not keyboard-operable

- Location: `src/features/launcher/components/SessionTimeline.tsx:307-311`
- Severity: Medium
- Category: Accessibility
- Description: The “思考” disclosure control is a clickable `<div>` with no button semantics, no keyboard handler, and no expanded state exposure.
- Impact: Keyboard-only users cannot open or close the reasoning block. Screen readers do not get an actionable control.
- WCAG/Standard: WCAG 2.1 A `2.1.1 Keyboard`; WCAG 2.1 A `4.1.2 Name, Role, Value`
- Recommendation: Replace it with a real `<button>` and expose expanded/collapsed state.
- Suggested command: `/harden`

#### 8. Settings section switcher lacks state semantics

- Location: `src/features/settings/SettingsPage.tsx:2573-2584`
- Severity: Medium
- Category: Accessibility
- Description: The section switcher visually behaves like tabs or segmented navigation, but active state is only a CSS class. Playwright DOM sampling confirmed there is no `aria-current`, `aria-selected`, or tab relationship.
- Impact: Screen reader users get eight identical buttons with no machine-readable indication of which section is active.
- WCAG/Standard: WCAG 2.1 A `4.1.2 Name, Role, Value`
- Recommendation: Implement a real tablist/tab/tabpanel pattern, or if it is navigation, expose `aria-current`.
- Suggested command: `/harden`

### Low-Severity Issues

#### 9. Secondary text contrast is too weak in multiple small-text surfaces

- Location: `src/features/launcher/launcher.css:80-93`, `src/features/launcher/launcher.css:694-699`, `src/features/settings/settings.css:111-117`
- Severity: Low
- Category: Accessibility
- Description: Several small labels sit below AA contrast for their size. Measured examples:
  - launcher status label `#8f9188` on white: `3.19:1`
  - settings kicker `#8a8f82` on white: `3.32:1`
  - workspace caret `#888c82` on pale background: `3.31:1`
  - launcher placeholder `#b1b1aa` on white: `2.16:1`
- Impact: Microcopy that carries structure or instruction becomes hard to read, especially on lower-quality displays or under transparency blur.
- WCAG/Standard: WCAG 2.1 AA `1.4.3 Contrast (Minimum)` for meaningful text
- Recommendation: Darken small labels, or reduce reliance on pale beige-on-white microcopy as a hierarchy tool.
- Suggested command: `/typeset`

#### 10. Hard-coded color sprawl undermines theming and consistency

- Location: `src/app/global.css:1-56`, `src/features/launcher/launcher.css`, `src/features/settings/settings.css`
- Severity: Low
- Category: Theming
- Description: Root tokens exist, but feature CSS still contains a large volume of direct literals. Counted occurrences:
  - `global.css`: 41 color literals
  - `launcher.css`: 257 color literals
  - `settings.css`: 223 color literals
- Impact: Theme changes become brittle, audits become slower, and visual drift accumulates between surfaces.
- WCAG/Standard: Design-system consistency issue.
- Recommendation: Pull repeated tones into semantic tokens and stop mixing token-driven styling with one-off literals.
- Suggested command: `/normalize`

#### 11. The launcher/settings visual language is generic and low-memory

- Location: `src/app/global.css:1-56`, `src/features/launcher/launcher.css:7-15`, `src/features/settings/settings.css:6-17`
- Severity: Low
- Category: Anti-Pattern
- Description: The product is dominated by safe frosted panels, beige neutrals, uniform rounded pills, and an overused default font stack. Nothing visually encodes why this tool is different from any other AI launcher/settings mock.
- Impact: The product looks unfinished, forgettable, and templated. That reduces trust for a tool whose core value is fast, confident command execution.
- WCAG/Standard: No direct WCAG violation.
- Recommendation: Remove generic glass treatment, strengthen hierarchy, pick a more deliberate typographic direction, and create one unmistakable visual idea.
- Suggested command: `/distill`

## Patterns And Systemic Issues

- Appearance settings are persisted before they are implemented. This creates fake affordances.
- Tokens exist, but feature styles still bypass them heavily. Theming is structurally weak.
- Small-text, pale-on-pale hierarchy is used everywhere. Readability drops first in the exact places users need orientation.
- The UI overuses rounded pills and frosted panels, flattening hierarchy into one generic treatment.
- Desktop constraints leaked into browser layout assumptions. The settings frame logic ignores narrow viewport reality.

## Positive Findings

- Settings page structure is materially better than the visual styling: it uses `main`, `header`, `nav`, `section`, and heading levels sensibly in `src/features/settings/SettingsPage.tsx`.
- There is explicit reduced-motion handling in both `src/app/global.css:302-307` and `src/features/launcher/launcher.css:570-583`.
- Heavy UI pieces are lazily loaded: `SettingsPage` in `src/app/App.tsx:1-10`, `SessionTimeline` and `MarkdownRenderer` in `src/features/launcher/components/LauncherFeedback.tsx:11-20`.
- Settings forms mostly use real labels and native controls rather than gratuitous custom widgets.
- Root-level design tokens exist; the problem is incomplete adoption, not total absence of a system.

## Recommendations By Priority

### Immediate

1. Label the launcher input properly and wire autocomplete semantics.
2. Fix popup semantics for workspace/agent/session controls.
3. Replace the thought disclosure `<div>` with a button.

### Short-term

1. Remove or implement theme/font-size settings.
2. Stop forcing the settings frame to `920px` in narrow browser contexts.
3. Raise minimum target sizes for launcher chrome and session dots.

### Medium-term

1. Refactor feature CSS away from hard-coded color literals.
2. Darken microcopy and tighten text hierarchy.
3. Reduce mutation-heavy resize measurement in the launcher.

### Long-term

1. Rework the visual direction so the product stops reading as generic AI glassware.
2. Give launcher and settings distinct hierarchy patterns instead of one repeated pill system.

## Suggested Commands For Fixes

- Use `/harden` to fix accessible names, keyboard operability, and popup semantics.
- Use `/adapt` to repair narrow-viewport behavior and target sizing.
- Use `/normalize` to connect settings to real theming behavior and consolidate tokens.
- Use `/typeset` to raise contrast and improve microcopy hierarchy.
- Use `/optimize` to reduce resize/layout measurement cost in the launcher.
- Use `/distill` to remove the generic glassy/pill-heavy visual noise before any polish pass.
